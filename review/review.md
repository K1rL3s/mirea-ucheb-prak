### Что проверено

Проект собран по README командой `javac` с `--release 17`. На JDK 17.0.12 прошли все 35 штатных проверок (`PASS: 35 checks`). Консольный вывод Java и Python для поезда 2041 совпал побайтно. Сохранённые планы также совпали после нормализации времени создания и зависимых от него идентификаторов. В плане 17 размещений, занято 24 ДФЭ из 25 (96 %), нужны три перестановки упоров.

На диаграмме есть десять сущностей логической модели, композиции и связи наследования. `Container20` и `Container40` наследуют `Container` и по-разному считают ДФЭ. Диаграмма также показывает реализации `LoadRule`. Планировщик получает список `List<LoadRule>` и проверяет по нему ограничения длины и массы. Порядок платформ и размещений хранится в `List`. Для поиска сущностей по ключу используется `Map`, для поиска повторов номеров контейнеров помогает `Set`. Сценарий запуска и вывода можно проследить в `Main`, проверку данных и распределение по платформам в `Planner`. Чтение JSON вынесено отдельно.

### Замечания

1. В `Dataset.read()` дробный `request_id` при преобразовании к `int` теряет дробную часть. В копии `train_2041.json` у `VLGU1000010` значение `1` заменено на `1.5`. Java-версия отнесла контейнер к заявке 1 и включила в план поезда 2041. В план Python этот контейнер не попадает. Для идентификаторов и порядковых номеров нужна проверка целого числа и диапазона `int`. В тесте с `request_id: 1.5` стоит ожидать ошибку с именем поля. [Dataset.java, строки 90-99](https://github.com/Wo0zZ1/container-load-planning/blob/f28e500e31f3f67e6ffd64da032cd13cb7a6ae45/src/java/Dataset.java#L90-L99)

2. Проверка массы отклоняет пропуск значения, ноль и превышение предела типоразмера. Значение `-28.4` у `VLGU1000010` прошло проверку в обеих версиях и уменьшило суммарную массу на платформе. В Java достаточно отклонять `grossMass <= 0` и добавить тест с отрицательным значением. Если править и Python, изменение версии КТ2 по памятке нужно вынести в отдельный коммит. [Container.java, строки 30-41](https://github.com/Wo0zZ1/container-load-planning/blob/f28e500e31f3f67e6ffd64da032cd13cb7a6ae45/src/java/Container.java#L30-L41), [PlatformLoad.java, строки 17-23](https://github.com/Wo0zZ1/container-load-planning/blob/f28e500e31f3f67e6ffd64da032cd13cb7a6ae45/src/java/PlatformLoad.java#L17-L23), [checks.py, строки 12-20](https://github.com/Wo0zZ1/container-load-planning/blob/f28e500e31f3f67e6ffd64da032cd13cb7a6ae45/src/checks.py#L12-L20)

3. Готовый `LoadPlan` копирует список `loads`. Сами объекты `PlatformLoad` можно менять. В проверке к платформе с одним 20-футовым контейнером через `plan.loads().get(0).tryAdd(...)` добавлен второй такой же. В сводке итог вырос с 1 до 2 ДФЭ, в `placements` для JSON по-прежнему 1 размещение. Стоит зафиксировать загрузку каждой платформы при создании плана и выдавать её только для чтения. [LoadPlan.java, строки 18-41](https://github.com/Wo0zZ1/container-load-planning/blob/f28e500e31f3f67e6ffd64da032cd13cb7a6ae45/src/java/LoadPlan.java#L18-L41), [PlatformLoad.java, строки 15-24](https://github.com/Wo0zZ1/container-load-planning/blob/f28e500e31f3f67e6ffd64da032cd13cb7a6ae45/src/java/PlatformLoad.java#L15-L24)

4. В UML пропущены ассоциации по полям. `Placement` хранит ссылку на платформу, `LoadPlan` хранит ссылку на поезд, `Planner` хранит список `LoadRule`. Эти поля уже есть на диаграмме. Предлагаю соединить `Placement` с `Platform`, `LoadPlan` с `Train` и `Planner` с `LoadRule`, проставив кратности. Например, у размещения одна платформа, а у платформы может быть несколько размещений. [classes.drawio, строки 345-398](https://github.com/Wo0zZ1/container-load-planning/blob/f28e500e31f3f67e6ffd64da032cd13cb7a6ae45/models/classes.drawio#L345-L398)

### Что проверено

Сверил связи аренды, сегментов и правил доплат на диаграмме с кодом. `DrivingSegment` и `WaitingSegment` наследуют `RentalSegment`: округление длительности общее, минуты учитываются отдельно для движения и ожидания. `OutsideZoneRule` и `LowFuelRule` реализуют `SurchargeRule`, участвуют в расчёте и срабатывают на второй аренде контрольного примера. `List` сохраняет порядок зон, `Map` связывает записи по идентификаторам, `Set` используется при поиске снятых ракурсов. По коду можно отдельно проследить чтение данных в `JsonReader`, расчёт в `Rental` и формирование вывода в `Main`.

Проверил оба описанных в README варианта запуска: с `data.json` в текущем каталоге и с явным путём. Исходники собрал на JDK 26.0.2.1 с `javac --release 25` и доступной локально версией Jackson 2.19.2. Сборку JAR по README с Maven и Jackson 2.23.0 в этой среде проверить не удалось. На штатном наборе стоимость трёх аренд составила 500,10, 1311,70 и 710,70 руб. После нормализации переносов строк весь вывод совпал с Python и примером из README.

### Замечания

1. **Дробный идентификатор бронирования принимается как целый.** У аренды 1 заменил `booking_id: 1` на `booking_id: 1.5`. Программа привязала аренду к бронированию 1 и завершилась без ошибки. Стоит проверить, что значение является целым числом в диапазоне `int`, перед преобразованием. При ошибке полезно указать имя поля и неверное значение. [JsonReader.java, чтение бронирования](https://github.com/K1rL3s/mirea-ucheb-prak/blob/2faad5d298aaff3345b7bd2ec36089691b59ea55/src/java/src/main/java/ru/mirea/carsharing/JsonReader.java#L65-L70), [преобразование идентификатора](https://github.com/K1rL3s/mirea-ucheb-prak/blob/2faad5d298aaff3345b7bd2ec36089691b59ea55/src/java/src/main/java/ru/mirea/carsharing/JsonReader.java#L122-L133).

2. **Машина может стать свободной без фотоосмотра при сдаче.** У аренды 1 удалил осмотр при сдаче и относящиеся к нему фотографии, а у всех ракурсов выставил `required: false`. Программа вывела «Фотоосмотр при сдаче: полный» и перевела машину в статус «свободен». README указывает, что отсутствие осмотра должно приводить к обслуживанию. Предлагаю отдельно проверять наличие осмотра и учитывать результат при формировании сообщения и выборе статуса. [Rental.java, строки 54-60](https://github.com/K1rL3s/mirea-ucheb-prak/blob/2faad5d298aaff3345b7bd2ec36089691b59ea55/src/java/src/main/java/ru/mirea/carsharing/domain/rental/Rental.java#L54-L60), [Main.java, строки 50-55](https://github.com/K1rL3s/mirea-ucheb-prak/blob/2faad5d298aaff3345b7bd2ec36089691b59ea55/src/java/src/main/java/ru/mirea/carsharing/Main.java#L50-L55), [README](https://github.com/K1rL3s/mirea-ucheb-prak/blob/2faad5d298aaff3345b7bd2ec36089691b59ea55/src/java/README.md#L75).

3. **Зона без вершин загружается и прерывает расчёт.** Удалил из входного файла вершины зоны 1. Чтение данных завершилось, но при первой проверке зоны программа упала с `NoSuchElementException`. На диаграмме у зоны должно быть не менее трёх вершин. Предлагаю проверять это при создании `Zone` и указывать идентификатор зоны в сообщении об ошибке. [JsonReader.java, строки 52-56](https://github.com/K1rL3s/mirea-ucheb-prak/blob/2faad5d298aaff3345b7bd2ec36089691b59ea55/src/java/src/main/java/ru/mirea/carsharing/JsonReader.java#L52-L56), [Zone.java, строки 5-9](https://github.com/K1rL3s/mirea-ucheb-prak/blob/2faad5d298aaff3345b7bd2ec36089691b59ea55/src/java/src/main/java/ru/mirea/carsharing/domain/geo/Zone.java#L5-L9), [связь на диаграмме](https://github.com/K1rL3s/mirea-ucheb-prak/blob/2faad5d298aaff3345b7bd2ec36089691b59ea55/models/classes.puml#L103-L115).
